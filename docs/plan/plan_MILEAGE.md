# План: пробег авто не больше 400 000 км, иначе решение review (MILEAGE)

Учебная фича дня 1 (docs/README.md, ID `MILEAGE`). Правило из задачи: пробег
≤ 400 000 км — решение считается как сейчас; пробег > 400 000 км — решение
«как минимум review»: approve понижается до review, review и reject по LTV не
меняются. Семантика понижения — из docs/setup/code_map.md, раздел «Куда встанет
правило»; подтверждение заказчика — в вопросах 2 и 4 ниже.

Место реализации — `DecisionEngine::decide()`: единственная точка, где рождаются
правила решения. Данные для правила уже есть: валидатор нормализует пробег до
int (`ApplicationValidator.php:43–46, 78`), `$input['mileage']` доступен в
`AssessmentService::assess()`. Порог кладём в `backend/config/rules.php` рядом
с `max_mileage_km` — бизнес-числа в коде не хардкодим (AGENTS.md). Альтернатива
«правило внутри AssessmentService» отвергнута по code_map: правило жило бы вне
движка решений, а конфиг в AssessmentService не передаётся. Валидатор для этого
правила не подходит в принципе: его ошибка — это 422, а нужно решение review.

Ограничение из code_map: пробег > 500 000 км отбивается валидацией
(`max_mileage_km = 500000`, ответ 422) и до решения не доходит — новое правило
фактически работает только в окне 400 001–500 000 км.

## Риски

- **Сигнатура `decide()` ломает все точки вызова**: `AssessmentService.php:33`
  и `DecisionEngineTest` (`setUp()` + провайдер). Пропущенная точка —
  `ArgumentCountError`, красный `make test`. Шаги 3–6 — одна пачка изменений.
- **Взаимодействие с `max_mileage_km = 500000`**: правило достижимо только в
  окне 400 001–500 000 км; если кто-то позже поменяет `max_mileage_km`, окно
  молча изменится. Сам ключ в этой задаче не трогать — порог меняется только с
  решением риск-менеджмента (AGENTS.md).
- **Понижение, а не безусловный review**: если реализовать «пробег выше порога
  → return REVIEW», заявки из reject-зоны по LTV ошибочно станут review.
  Пинать тестом 400001 + reject-LTV → reject.
- **`approved_limit` молча обнуляется** для заявок окна 400 001–500 000 при
  хорошем LTV: раньше могли быть approve + лимит, теперь review + 0. Это
  намеренное изменение ответа API; клиенты, рассчитывавшие на approve, увидят
  другой вердикт.
- **Оба эндпоинта меняются одновременно**: `/api/ltv` и `/api/applications` оба
  зовут `assess()` (`ApplicationController.php:28, 59`) — разделить поведение
  текущим планом нельзя.
- **Граница включительная**: «не больше 400 000» принято как ≤ (400 000 —
  approve). Если риск-менеджмент имел в виду строго «<», кейс 400 000 станет
  review — меняется одно сравнение и одно ожидание теста, но только после
  явного решения человека (вопрос 1).
- **Не чинить попутно расхождение LTV-границы**: докблок `DecisionEngine`
  (строки 10–12) обещает `LTV <= approve_max → approve`, код делает строго `<`,
  и ровно 60.0 даёт review (code_map, строка 32). Это отдельное решение
  риск-менеджмента, в MILEAGE не входит.
- **Цепочка артефактов**: после плана идут `intent_MILEAGE.md` и
  `spec_MILEAGE.md` (docs/README.md); перед реализацией план сверяется со
  спекой и дополняется (docs/plan/README.md). Реализовывать до появления спеки
  — значит опередить цепочку.

Что не входит (осознанно):

- фронтенд: подсказки и валидация про 400 000 км в форме;
- причина review в ответе API (decision остаётся строкой без объяснений);
- `max_mileage_km`, LTV-пороги, `ltv_by_age` (LOAN-12) — без изменений;
- БД, репозиторий, сиды: решение считается до `save()`, схема не меняется;
- поведение при пробеге > 500 000 (остаётся 422);
- документы вне этого файла (`intent/`, `spec/` пишутся по своей цепочке).

## Чего не хватает (без заказчика не ответить)

   (включительное «не больше»), а review начинается с 400 001.

3. Пустой пробег: подтвердить, что отсутствующее поле остаётся ошибкой 422, а
   пустая строка из формы по-прежнему превращается в 0 (существующий квирк) —
   или пустое поле тоже должно отклоняться / давать review.
4. Семантика «иначе review»: подтвердить, что reject по LTV при пробеге
   > 400 000 остаётся reject, то есть правило только понижает approve до review
   и никогда не «повышает» reject.
5. Оба эндпоинта: правило применится и к `/api/ltv`, и к `/api/applications`
