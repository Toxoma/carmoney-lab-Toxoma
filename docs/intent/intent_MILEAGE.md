# Intent: пробег авто не больше 400 000 км, иначе решение review (MILEAGE)

## Зачем

Учебная фича (docs/README.md, ID `MILEAGE`): в расчёт решения по заявке
добавить проверку пробега. Сейчас решение считается только из LTV
(`DecisionEngine::decide(float $ltv)`), пробег участвует лишь в валидации
диапазона 0..500 000 км (`ApplicationValidator`, ответ 422). Задача —
учитывать высокий пробег при принятии решения: авто с пробегом выше
порога не должно получать approve безусловно.

## Что делаем (интент, не спека)

Правило: если решение по LTV — approve и пробег выше порога 400 000 км,
понижаем решение до review. Пробег — понижающий модификатор поверх LTV,
не независимый сигнал:

- approve + пробег выше порога → review;
- review по LTV → review (без изменений);
- reject по LTV → reject (правило никогда не «повышает» reject до review);
- LTV рассчитывается как сейчас, пробег в расчёт LTV не входит.

Место реализации — `DecisionEngine::decide()` (единственная точка, где
рождаются правила решения), порог — в `backend/config/rules.php` новым
ключом рядом с `max_mileage_km` (бизнес-числа не хардкодим, AGENTS.md).

## Что подтверждено заказчиком (вопросы Grill Me, план docs/plan/plan_MILEAGE.md)

1. **Семантика «иначе review» — понижение**: reject по LTV при высоком
   пробеге остаётся reject (вопрос 3 — ответ «да»).
2. **Пробег — модификатор, не сигнал**: LTV review-зоны при высоком
   пробеге остаётся review, без ужесточения до reject (вопрос 4).
3. **Оба эндпоинта**: правило применяется и к `/api/ltv`, и к
   `/api/applications` через общий `assess()` — так и задумано, разделить
   поведение не требуется (вопрос 6 — ответ «оставить»).
4. **Состав scope** — как в плане: без фронтенда, без причины review в
   ответе API, без изменений `max_mileage_km`, LTV-порогов, БД, репозитория,
   сидов (вопрос 5).

## Открытые вопросы к риск-менеджменту (блокирующие валидацию, не намерение)

По AGENTS.md пороги и их границы не выбираются агентом. Каждый вопрос ниже
закрыт решением риск-менеджмента; до ответа намерение фиксирует рабочие
варианты, план реализуется с ними, смена варианта — одна правка сравнения
и одного ожидания теста.

1. **Граница 400 000**: включительная («не больше» = ≤, ровно 400 000 —
   approve, review с 400 001) или строгая (<). Рабочий вариант плана —
   включительная (docs/plan/plan_MILEAGE.md, строка 119).
2. **Отсутствующий / пустой пробег**: текущее поведение (поле отсутствует
   → −1 → 422; пустая строка из формы → `(int)'' = 0`) — подтвердить как
   правильное или изменить отдельной задачей. В MILEAGE не меняется.
3. **Ужесточение**: нужен ли сценарий «высокий пробег + LTV review-зоны →
   reject»? Базовая семантика (п. «Что делаем») — нет, подтверждено
   вопросом 4; любое ужесточение — отдельное решение риск-менеджмента.
4. **Значение порога 400 000**: подтверждение, что число согласовано
   риск-менеджментом и ляжет в `rules.php` новым ключом. В репозитории
   согласования нет — значение взято из текста задачи.

## Ограничения (из code_map / плана)

- Пробег > 500 000 км отбивается валидацией (422) до расчёта решения —
  правило фактически работает только в окне 400 001–500 000 км.
- `max_mileage_km`, LTV-пороги, `ltv_by_age` (LOAN-12) в этой задаче не
  меняются (AGENTS.md: менять пороги ради зелёного `make test` нельзя).
- Расхождение LTV-границы (докблок обещает `<= 60.0 → approve`, код
  делает строгий `<`) не чиним попутно — отдельное решение.
